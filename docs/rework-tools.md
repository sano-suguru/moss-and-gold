# 検証の道具の作り直し（七巡目の前）

「手直し → 複数シードで回す → 比べる → 原因を追う」の一巡を速くするために、分析の道具と構造を作り直した。
**シミュレーションの振る舞いは変えていない**（前の版と、同じシードからの記録と状態が1バイトも違わないことを `npm run ab` で確かめた。下の「確かめたこと」）。

## 時間（前と後）

環境：CPU 4つ、Node 22。前は作り直す前のコミット 4945897、後は作り直したあと（下の「測り方」）。

| 作業 | 前 | 後 | どうして速くなったか |
|---|---:|---:|---|
| 1. 20日目に飢え死にした大ネズミ1匹の直前の様子を見るまで | **51秒**（autopsy で0日目から20日目まで回す） | **7秒**（`npm run probe -- deaths --seed seed7 --kind 2 --cause starve --day 19`。いまの版で回した batch があるときも、コードを直した直後に前の版の19日目の状態から続けるときも、7.3秒） | 1日ごとの状態の保存庫から19日目の状態を読み、1日だけ回す |
| 2. 小さな手直し1つの効き目を8シードで見るまで | **277秒**（8シード×25日の batch。前の版の batch はあるものとして）＋ compare | **127秒**（`npm run check` 62秒 ＋ `npm run ab -- --preset quick` 65秒） | 前の版の10日目の状態から、いまの版だけを8日ぶん回す（前の版の続きは保存庫から）。同じ状態から分かれた対にした比較なので、短い日数でも差が見え、差がばらつきに埋もれていないかの目安も付く |
| 3. 16シード×25日の比較 | **570秒**（batch）＋ compare | **496秒**（`npm run ab -- --preset final`。比較の表まで） | 前の版は保存庫から（回さない）。かかる時間の長いシードから回す（前の回の1日あたりの秒数から見積もる）。report を並べて作る |
| 4. `npm test` | **31秒** | **14.5秒**（`TEST_FULL=1` でもとの確かめ：29秒） | 保存からの再現を、0日目から6日回す代わりに、決まった5日目の状態（test/fixtures）から二つのプロセスで。地形の検査で同じ地形を作り直さない |

シミュレーションそのものの速さ（地上1日あたり約3〜5秒）は、ほぼ変わらない。時間の内訳（`node --cpu-prof`、seed4 の10日）が平らで（いちばん大きい生き物の1歩の本体でも9％、ウィスプ6％、マナ5.5％、見たマスの更新5％、水5％、群れの一覧5％）、展開を1バイトも変えずに大きく削れる所がなかった。
見たマスの更新（まだ見ていないマスだけを見る、光源を一度だけ集める）と、群れの身元の控え（群れない種は控えない）だけ軽くした。速さは、決まった仕組みで「回さずに済ませる」ことで稼いでいる。

## しくみ

### 版と保存庫（runs/.cache）

- **版（simHash）**：`tools/analysis/lib/engine.ts`（画面なしで進める入口。1刻みごとに `step` と、20刻みごとに `updateSeen`）からたどれるソース（src/ の world、ecology、eco/*、mapgen など）の**中身**のハッシュ。中身だけで決まるので、git のコミットでも作業中のファイルでも、同じ中身なら同じ版。
- **道具の版（binHash）**：組み立てた道具（記録の仕方＝sim.ts なども含む）の中身のハッシュ。
- 道具はすべて `node tools/analysis/launch.mjs <道具>` で組み立てて `runs/.cache/bin/<道具>-<binHash>.js` に置く。書き換えないので、batch の最中にソースを直しても、回っているものに響かない（以前は build/sim.js を使っていて、batch の最中は作り直せなかった）。
- git の参照（`--base HEAD~1`、`--ref` など）は、その版の **src/ だけ**を `runs/.cache/src/<コミット>/` に取り出し、**いまの記録の仕方**と組み合わせて組み立てる。前の版といまの版を同じ記録の仕方で比べられる（作り直す前のコミットも、そのまま比べられる）。

| 場所 | 中身 | 使い回す規則 |
|---|---|---|
| `runs/.cache/snap/<simHash>/a<上限>/<シード>/dNNN.json.gz` | 最初から一つの版だけで回した（混じりけのない）状態。地上の1日ごと | 同じ版・同じ冒険者の上限・同じシード |
| `runs/.cache/run/<binHash>/a<上限>/<シード>/0/` | 最初から回した結果（sim の書き出しと同じ形、`snap/` に1日ごとの状態） | 同じ道具の版。日数が足りなければ `--resume` で続きから |
| `runs/.cache/run/<binHash>/a<上限>/<シード>/f<日>-<simHash>/` | 別の版（simHash）のその日の状態から続けた結果。その日までの記録は前の版のものを写してある | 同じ道具の版・同じ分かれ目 |

作り直す時機は**規則だけ**で決まる：版が違えば別の場所なので使わない。「最後に作ってからの時間」では決めない（CLAUDE.md の「キャッシュの作り直しの時機」と同じ考え方）。
進め方（lib/engine.ts）や記録の仕方（sim.ts）を直すと、ハッシュが変わって保存庫は使われなくなる（回し直しになる）。

続きから回しても結果が通しと1バイトも違わないように、sim の記録は**刻みが DAY_TICKS/4 の倍数のとき**にした（以前は0.3日目から1/4日ごとで、続きから回すと記録の刻みがずれた）。
`npm run ab -- --resume-check` は、状態だけでなく samples・deaths・births・settle・events の記録も通しと一致することを確かめる。

### 対にした比較（ab --fork、preset quick）

前の版の F 日目の状態から、前の版といまの版を D 日目まで続け、同じシードどうしの差を見る。
- 前の版の続きは、前の版を最初から回した結果そのもの（決定的なので）。保存庫にあれば回さない。
- いまの版は F→D の (D−F) 日ぶんだけ回す。
- 分かれる前の記録は同じなので、compare は `--since F` で F 日目より後だけを比べる。

`compare --paired`（ab が付ける）は、指標ごとに次を並べる（lib/stats.ts）：
- 前の合計・後の合計、シードごとの差の平均と、その90％区間（シードを選び直すブートストラップ。乱数の種は決まっていて毎回同じ）
- 差の中央値、増えたシード／減ったシードの数
- 1シードの寄与：差の絶対値の合計のうち、いちばん大きい1シードの割合と、そのシードを除くと差の合計の向きが変わるか
- 差の分布の小さな図（小さい順、`|` が0）
- 目安：90％区間が0をまたがず、符号検定の両側 p が0.1未満で、1シードを除いても向きが変わらないときだけ「はっきり」。どれかが欠ければ「ばらつきの内」

16シードの合計が1シードの出来事（seed17 だけでコボルトが46匹倒された、など）に引っ張られているかどうかは、「1シードの寄与」の列でわかる。

### 早めの確かめ（npm run check）

`tools/analysis/checks.ts` に、シードの組・始まりの日・終わりの日・判定を書く。前の版（既定 HEAD）の始まりの日の状態から、いまの版で終わりの日まで回し（保存庫を使う）、記録で判定する。
同じ (シード, 始まり, 終わり) は確かめどうしで共有する。いまは4シード（かしたれ、seed8、abc、seed7）を10日目から18日目まで回して、
貢ぎ物の取り立て、集落の蓄え、コボルトの住処、大ネズミが絶えないこと、四つの帳簿を見る。新しい流れを足したら、起きることがわかっているシードと日を選んで確かめを足す。

### 調べ物（npm run probe）

`lib/open.ts` の `openAt(シード, 刻み)` が、次の順で状態を探して、そこから目当ての刻みまで進める（どこから始めたかを表示する）：
1. `--run` で指定した回の状態
2. いまの版で最初から回した状態
3. いまの版で、前の版の状態から続けた回の状態
4. 前の版（`--base`、既定 HEAD）で最初から回した状態から、いまの版で続ける（コードを直した直後）
5. なければ最初から回す（1日ごとの状態は保存庫に置くので、次からは速い）

| 道具 | 使い捨てのスクリプトの代わりに |
|---|---|
| `probe deaths` | （`--day 19` で 19.0〜20.0日、20日目）死ぬ前の約1,000刻みを持っておき、死んだら様子（死因、状態、直前に多かった状態、足もと、止まっていたか、食べ物・住みかまでの道のり）で分ける。例は直前の履歴つき |
| `probe life` | ある個体の一生（生まれた日は1日ごとの状態の番号から探す）。状態が変わるたびの1行と、20刻みごとの記録 |
| `probe calls` | メソッドを包んで、呼び出しの回数・時間・戻り値の内訳を日ごとに数える（取り立ての送り出しがなぜ空振りするか、など） |
| `probe look` | ある刻み・場所（または個体）のまわりの地形と生き物の字の地図と一覧、住みついた群れ。`--expr` で式の値 |
| `probe stuck` | 動こうとして進めない場所の地図（以前の stuckmap） |

以前の autopsy と stuckmap は、0日目から `w.step()` だけで進めていて、sim（20刻みごとに `updateSeen` も呼ぶ）と展開が違っていた。いまはどれも lib/engine.ts の同じ進め方なので、batch で見た死と同じ死を調べられる。

### 回し直さずに値を計算する（npm run metric）

sim は地上の1日ごとの状態を `snap/` に残す（gzip で1つ50〜90KB、16シード×25日で約26MB。保存庫と回したフォルダはハードリンクで同じものを指す）。
記録（samples.jsonl など）に無い値が後から要るときは、`npm run metric -- --runs <回> --expr "式"` で1日ごとの状態を読み直して計算する（状態1つにつき約0.3秒、シードごとに別のプロセスで同時に）。二つの回を渡せば、対にした比較の目安も付く。
よく使うものは metric.ts の `NAMED` に名前をつけて置く（campStore、vassalCamps、warrenStore、hungryRats など）。

### src/ecology.ts の分割

約9,900行の1ファイルだった Ecology を、クラスの本体（状態のフィールド、保存しない控え、定数、型。約770行）と、種・仕組みごとのメソッドのファイル（src/eco/*.ts、35ファイル）に分けた。
各ファイルは `export function 名前(this: Ecology, …)` でメソッドを書き、末尾で `declare module '../ecology' { interface Ecology { … } }` と `Object.assign(Ecology.prototype, { … })` で足す。src/eco/index.ts がすべてを読み込み、world.ts が index を読む。
中身は機械的に移しただけ（`private` は外した）。const enum（Kind など）は esbuild がファイルをまたいで埋め込む。

## 確かめたこと

- `npm run ab -- --base 4945897 --seeds abc,かしたれ,seed4,seed7 --days 25`（作り直す前のコミットの src/ と、いまの src/ を、同じ記録の仕方で）：ecology の分割と軽くした二つの所を含めて、4シードとも samples.jsonl と checkpoint.json が25日目まで1バイトも違わない
- 作り直した sim の checkpoint は、作り直す前の sim の checkpoint と1バイトも違わない（abc、2日）
- `npm run ab -- --resume-check 7 --seeds かしたれ,abc --days 12`：状態と記録が通しと一致
- `npm test`（21項目すべて OK）、`TEST_FULL=1 npm test`（もとの0日目から6日の保存からの再現）も OK
- `node build.mjs`（ゲームの1ファイル）も組み立てられる
- 四つの帳簿：16シード×25日でずれ0

`npm run check` の確かめは、前の版の batch で判定の目安を確かめてから置いた。初めに置いた「大ネズミが絶えない（最後の記録で1匹以上）」は、前の版でも大ネズミが0匹と数匹を行き来する（abc、かしたれ）ために届かなかったので、「来つづける」に替えた。
確かめを足すときも、まず前の版で届くことを `npm run check -- --only <名前>` で見ておく（前の版といまの版が同じなら、保存庫の結果を使うので数秒）。

## 測り方

前：作り直す前のコミット 4945897 で、`npm test`、`npm run autopsy -- --seed seed7 --days 20 --kind 2 --cause starve`、`npm run batch`（8シード×25日、16シード×25日）を一つずつ回して測った（runs/baseline）。
16シードは compare の目安と同じ組（abc、かしたれ、はじまりの洞窟、seed4〜8、seed40、seed41、seed18、seed27、seed23、seed35、seed17、seed30。lib/seeds.ts の SEEDS16）。

後：作り直したコミットで16シード×25日を一度回して保存庫に入れ（「前の回」）、そのあと小さな手直し（`Ecology.GOBLIN_MIN_FOOD` を 1800 → 1500）を入れた状態で、次の順に一つずつ測った（runs/after）：
`npm test` → `npm run probe -- deaths …`（直した直後。前の版の状態から）→ `npm run check` → `npm run ab -- --preset quick` → `npm run ab -- --preset final` → `npm run probe -- deaths …`（final がいまの版の状態を保存庫に置いたあと）。

この手直しの効き目は、quick（8シード、10→18日）では「ゴブリン：中で生まれた」（5対0）と「オーク：飢えて去った」（5対0）が「はっきり増」、
final（16シード×25日）では「オーク：取り立て（回）」（5対0）と「取り立てた食べ物」（7対2）が「はっきり増」で、残りの29の指標は「ばらつきの内」だった。

注意：保存庫が空のとき（作り直した直後や、`runs/.cache` を消したあと、進め方 lib/engine.ts や記録の仕方 sim.ts を直したあと）は、前の版の結果もまず回すので、そのぶん長くかかる（quick なら前の版の8シード×18日、final なら16シード×25日）。

## そのほか

- batch の出力の既定の名前は `runs/batch-<日時（秒まで）>`、ab は `runs/ab-<preset>-<日時>`。回ごとに分かれ、組み立てた道具も保存庫の中なので、二つの batch を同時に回してもぶつからない（同じ結果を作る仕事は、ロックのフォルダで一つにまとまる）。
- 前の版との比較（ab、check、probe の前の版）は、前の版の src/ と**いまの**記録の仕方を組み合わせる。記録の仕方を変えた（sim.ts に値を足した）ときも、前の版を同じ記録で回し直して比べられる。
- 細かい使い方は各道具の先頭のコメントと、CLAUDE.md の「よく使うコマンド」「分析の流れ」。
