# 分析ツールのキャッシュのしくみ（runs/.cache）

分析ツールは、実行結果と日次スナップショットを、ソースの中身のハッシュごとのキャッシュに残して再利用する。各ツールの使い方は、そのファイルの先頭のコメントにある。A/B 比較の判定のしかたは tools/analysis/lib/stats.ts の先頭のコメント。

## バージョン

- **シミュレーションのバージョン（simHash）**：画面なしで進める入口 `tools/analysis/lib/engine.ts`（1 tick ごとに世界を進め、200 tick ごとにプレイヤーに見えたタイルを更新する）からたどれるソース（src/ の world、ecology、eco/*、mapgen など）の**中身**のハッシュ。中身だけで決まるので、git のコミットでも作業中のファイルでも、同じ中身なら同じバージョンになる。
- **ツールのバージョン（binHash）**：ビルドしたツールの中身のハッシュ。ログ出力（sim.ts）なども含む。
- ツールはすべて `node tools/analysis/launch.mjs <ツール名>` でビルドし、`runs/.cache/bin/<ツール名>-<binHash>.js` に置く。置いたものは書き換えないので、batch の最中にソースを直しても、実行中のものには影響しない。
- git の参照（`--base HEAD~1`、`--ref` など）を渡すと、そのコミットの **src/ だけ**を `runs/.cache/src/<コミット>/` に取り出し、**作業ツリーのログ出力**と組み合わせてビルドする。なので、ベースと作業ツリーを同じログ出力で比べられる。sim.ts に値を足したときも、ベースを同じログ出力で実行し直して比べられる。

## 置き場所と、再利用の条件

| 場所 | 中身 | 再利用の条件 |
|---|---|---|
| `runs/.cache/snap/<simHash>/a<上限>/<シード>/dNNN.json.gz` | 0日目から一つのバージョンだけで実行した状態。ゲーム内の1日ごと | 同じバージョン、同じ冒険者の一行の上限、同じシード |
| `runs/.cache/run/<binHash>/a<上限>/<シード>/0/` | 0日目から実行した結果（sim の出力と同じ形式。`snap/` に日次スナップショット） | 同じツールのバージョン。日数が足りなければ `--resume` で続きを実行する |
| `runs/.cache/run/<binHash>/a<上限>/<シード>/f<日>-<simHash>/` | 別のバージョン（simHash）の、その日のスナップショットから続けた結果。その日までのログはベースのものをコピーしてある | 同じツールのバージョン、同じ分岐点 |

- 無効化は**規則だけ**で決まる。バージョンが違えば置き場所が別なので使われない。「最後に作ってからの時間」では決めない（CLAUDE.md の「キャッシュの無効化の条件」と同じ考え方）。
- 実行エンジン（lib/engine.ts）やログ出力（sim.ts）を直すと、ハッシュが変わり、それまでのキャッシュは使われなくなる。ベースもまず実行し直すので、その分だけ時間がかかる（quick ならベースの8シード×18日、final なら16シード×25日）。
- 日次スナップショットは gzip で1つ50〜90KB（16シード×25日で約26MB）。キャッシュと実行の出力フォルダは、ハードリンクで同じファイルを指す。
- 中断・再開しても結果が通しの実行と1バイトも違わないように、sim のログは、tick が `DAY_TICKS/4` の倍数のときに書く。`npm run ab -- --resume-check` は、状態だけでなく、samples・deaths・births・settle・events のログも通しの実行と一致するかを確かめる。
- 実行の出力は、batch なら `runs/batch-<日時>`、ab なら `runs/ab-<preset>-<日時>` に置く。実行ごとにフォルダが分かれるので、二つの batch を同時に実行してもぶつからない（同じ結果を作るジョブは、ロック用のフォルダで一つにまとまる）。
- クラウドのセッションでは、main のキャッシュを GitHub Release「sim-cache」から取得する（tools/analysis/simcache.mjs）。置き場所が中身のハッシュで決まるので、取得したものも、手元で実行したものと同じように使われる。

## キャッシュの使われ方

- **A/B 比較（`ab --fork`、`--preset quick`）**：ベースの F 日目のスナップショットから、ベースと作業ツリーのそれぞれで D 日目まで続け、同じシード同士で比べる。ベースの続きは、ベースを0日目から実行した結果そのもの（決定的なので）で、キャッシュにあれば実行しない。作業ツリーは F→D の分だけ実行する。分岐する前のログは同じなので、比べるのは F 日目より後だけ（compare の `--since F`）。
- **調査（`probe`）と `openAt(シード, tick)`（lib/open.ts）**：次の順に状態を探し、そこから目当ての tick まで進める（どこから始めたかを表示する）。
  1. `--run` で指定した実行のスナップショット
  2. 作業ツリーのバージョンで0日目から実行したスナップショット
  3. 作業ツリーのバージョンで、ベースのスナップショットから続けた実行のスナップショット
  4. ベース（`--base`、既定 HEAD）で0日目から実行したスナップショット。そこから作業ツリーのバージョンで続ける（コードを直した直後はこれになる）
  5. どれも無ければ0日目から実行する（日次スナップショットをキャッシュに置くので、次からは速い）
- **ログに無い値（`metric`）**：日次スナップショットを読み直して計算する（1つにつき約0.3秒。シードごとに別のプロセスで並列に実行する）。よく使う式は metric.ts の `NAMED` に名前を付けて置く。
- **短い確認（`check`）**：checks.ts の項目ごとに、ベースの開始日のスナップショットから作業ツリーのバージョンで終了日まで実行する。同じ（シード、開始日、終了日）の実行は、項目どうしで共有する。項目を足すときは、まずベースで満たせることを `npm run check -- --only <名前>` で確かめる（バージョンが同じならキャッシュの結果を使うので数秒）。
