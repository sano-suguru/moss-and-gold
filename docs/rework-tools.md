# 検証ツールの作り直し（七巡目の前）

「変更 → 複数シードで実行 → 比較 → 原因の調査」のサイクルを速くするために、分析ツールと構造を作り直した。
**シミュレーションの挙動は変えていない**（ベースと、同じシードからのログと状態が1バイトも違わないことを `npm run ab` で確かめた。下の「確かめたこと」）。

## 所要時間（前と後）

環境：CPU 4つ、Node 22。前は作り直す前のコミット 4945897、後は作り直したあと（下の「測り方」）。

| 作業 | 前 | 後 | 速くなった理由 |
|---|---:|---:|---|
| 1. 20日目に飢え死にした大ネズミ1匹の直前の様子を見るまで | **51秒**（autopsy で0日目から20日目まで実行） | **7秒**（`npm run probe -- deaths --seed seed7 --kind 2 --cause starve --day 19`。作業ツリーのバージョンで実行した batch があるときも、コードを直した直後にベースの19日目のスナップショットから続けるときも、7.3秒） | 日次スナップショットのキャッシュから19日目の状態を読み、1日だけ実行する |
| 2. 小さな変更1つの効果を8シードで見るまで | **277秒**（8シード×25日の batch。ベースの batch はあるものとして）＋ compare | **127秒**（`npm run check` 62秒 ＋ `npm run ab -- --preset quick` 65秒） | ベースの10日目のスナップショットから、作業ツリーのバージョンだけを8日分実行する（ベースの続きはキャッシュから）。同じ状態から分岐した A/B 比較なので、短い日数でも差が見え、差がばらつきに埋もれていないかの判定も付く |
| 3. 16シード×25日の比較 | **570秒**（batch）＋ compare | **496秒**（`npm run ab -- --preset final`。比較の表まで） | ベースはキャッシュから（実行しない）。所要時間の長いシードから実行する（前回の1日あたりの秒数から見積もる）。report を並列に作る |
| 4. `npm test` | **31秒** | **14.5秒**（`TEST_FULL=1` で元のテスト：29秒） | ロード後の再現性のテストを、0日目から6日実行する代わりに、固定の5日目のスナップショット（test/fixtures）から2プロセスで。地形のテストで同じ地形を作り直さない |

シミュレーション自体の速さ（ゲーム内の1日あたり約3〜5秒）は、ほぼ変わらない。プロファイル（`node --cpu-prof`、seed4 の10日）が平らで（いちばん大きい生き物の1歩の本体でも9％、ウィスプ6％、マナ5.5％、見えたマスの更新5％、水5％、群れの一覧5％）、展開を1バイトも変えずに大きく削れる所がなかった。
見えたマスの更新（まだ見えていないマスだけを調べる、光源を一度だけ集める）と、群れの識別のキャッシュ（群れない種はキャッシュしない）だけ軽くした。速さは、決まった規則で「実行せずに済ませる」ことで稼いでいる。

## しくみ

### バージョンとキャッシュ（runs/.cache）

- **シミュレーションのバージョン（simHash）**：`tools/analysis/lib/engine.ts`（画面なしで進める入口。1 tick ごとに `step` と、200 tick ごとに `updateSeen`。作り直したときは20 tick ごとで、のちに docs/speed-experiments の D で200 tick ごとにした）からたどれるソース（src/ の world、ecology、eco/*、mapgen など）の**中身**のハッシュ。中身だけで決まるので、git のコミットでも作業中のファイルでも、同じ中身なら同じバージョン。
- **ツールのバージョン（binHash）**：ビルドしたツール（ログ出力＝sim.ts なども含む）の中身のハッシュ。
- ツールはすべて `node tools/analysis/launch.mjs <ツール名>` でビルドして `runs/.cache/bin/<ツール名>-<binHash>.js` に置く。書き換えないので、batch の最中にソースを直しても、実行中のものに影響しない（以前は build/sim.js を使っていて、batch の最中はビルドし直せなかった）。
- git の参照（`--base HEAD~1`、`--ref` など）は、そのコミットの **src/ だけ**を `runs/.cache/src/<コミット>/` に取り出し、**作業ツリーのログ出力**と組み合わせてビルドする。ベースと作業ツリーを同じログ出力で比べられる（作り直す前のコミットも、そのまま比べられる）。

| 場所 | 中身 | 再利用の条件 |
|---|---|---|
| `runs/.cache/snap/<simHash>/a<上限>/<シード>/dNNN.json.gz` | 0日目から一つのバージョンだけで実行した（混じりけのない）状態。ゲーム内の1日ごと | 同じバージョン・同じ冒険者パーティの上限・同じシード |
| `runs/.cache/run/<binHash>/a<上限>/<シード>/0/` | 0日目から実行した結果（sim の出力と同じ形式、`snap/` に日次スナップショット） | 同じツールのバージョン。日数が足りなければ `--resume` で再開 |
| `runs/.cache/run/<binHash>/a<上限>/<シード>/f<日>-<simHash>/` | 別のバージョン（simHash）のその日のスナップショットから続けた結果。その日までのログはベースのものをコピーしてある | 同じツールのバージョン・同じ分岐点 |

無効化は**規則だけ**で決まる：バージョンが違えば別の場所なので使わない。「最後に作ってからの時間」では決めない（CLAUDE.md の「キャッシュの無効化の条件」と同じ考え方）。
実行エンジン（lib/engine.ts）やログ出力（sim.ts）を直すと、ハッシュが変わってキャッシュは使われなくなる（再実行になる）。

中断・再開しても結果が通しの実行と1バイトも違わないように、sim のログは **tick が DAY_TICKS/4 の倍数のとき**に書くようにした（以前は0.3日目から1/4日ごとで、再開するとログを書く tick がずれた）。
`npm run ab -- --resume-check` は、状態だけでなく samples・deaths・births・settle・events のログも通しの実行と一致することを確かめる。

### A/B 比較（ab --fork、preset quick）

ベースの F 日目のスナップショットから、ベースと作業ツリーのそれぞれで D 日目まで続け、同じシード同士の差を見る。
- ベースの続きは、ベースを0日目から実行した結果そのもの（決定的なので）。キャッシュにあれば実行しない。
- 作業ツリーのバージョンは F→D の (D−F) 日分だけ実行する。
- 分岐する前のログは同じなので、compare は `--since F` で F 日目より後だけを比べる。

`compare --paired`（ab が付ける）は、指標ごとに次を並べる（lib/stats.ts）：
- 前の合計・後の合計、シードごとの差の平均と、その90％区間（シードを選び直すブートストラップ。乱数のシードは固定で毎回同じ）
- 差の中央値、増えたシード／減ったシードの数
- 1シードの寄与：差の絶対値の合計のうち、いちばん大きい1シードの割合と、そのシードを除くと差の合計の向きが変わるか
- 差の分布の小さな図（小さい順、`|` が0）
- 判定：90％区間が0をまたがず、符号検定の両側 p が0.1未満で、1シードを除いても向きが変わらないときだけ「はっきり」。どれかが欠ければ「ばらつきの内」

16シードの合計が1シードの出来事（seed17 だけでコボルトが46匹倒された、など）に引っ張られているかどうかは、「1シードの寄与」の列でわかる。

### 短い確認（npm run check）

`tools/analysis/checks.ts` に、シードの組・開始日・終了日・判定を書く。ベース（既定 HEAD）の開始日のスナップショットから、作業ツリーのバージョンで終了日まで実行し（キャッシュを使う）、ログで判定する。
同じ (シード, 開始日, 終了日) の実行は項目同士で共有する。いまは4シード（かしたれ、seed8、abc、seed7）を10日目から18日目まで実行して、
貢ぎ物の取り立て、集落の蓄え、コボルトの住処、大ネズミが絶えないこと、四つの保存則を見る。新しい挙動を足したら、起きることがわかっているシードと日を選んで項目を足す。

### 調査（npm run probe）

`lib/open.ts` の `openAt(シード, tick)` が、次の順で状態を探して、そこから目当ての tick まで進める（どこから始めたかを表示する）：
1. `--run` で指定した実行のスナップショット
2. 作業ツリーのバージョンで0日目から実行したスナップショット
3. 作業ツリーのバージョンで、ベースのスナップショットから続けた実行のスナップショット
4. ベース（`--base`、既定 HEAD）で0日目から実行したスナップショットから、作業ツリーのバージョンで続ける（コードを直した直後）
5. なければ0日目から実行する（日次スナップショットはキャッシュに置くので、次からは速い）

| ツール | 使い捨てのスクリプトの代わりに |
|---|---|
| `probe deaths` | （`--day 19` で 19.0〜20.0日、20日目）死ぬ前の約1,000 tick の履歴を持っておき、死んだら様子（死因、状態、直前に多かった状態、足もと、止まっていたか、食べ物・住みかまでの道のり）で分類する。例は直前の履歴つき |
| `probe life` | ある個体の一生（生まれた日は日次スナップショットの番号から探す）。状態が変わるたびの1行と、20 tick ごとのログ |
| `probe calls` | メソッドをラップして、呼び出しの回数・時間・戻り値の内訳を日ごとに数える（取り立ての送り出しがなぜ空振りするか、など） |
| `probe look` | ある tick・場所（または個体）のまわりの地形と生き物の文字マップと一覧、住みついた群れ。`--expr` で式の値 |
| `probe stuck` | 動こうとして進めない場所のマップ（以前の stuckmap） |

以前の autopsy と stuckmap は、0日目から `w.step()` だけで進めていて、sim（`updateSeen` も呼ぶ）と展開が違っていた。いまはどれも lib/engine.ts の同じ実行エンジンなので、batch で見た死と同じ死を調べられる。

### 再実行せずに値を計算する（npm run metric）

sim はゲーム内の1日ごとのスナップショットを `snap/` に残す（gzip で1つ50〜90KB、16シード×25日で約26MB。キャッシュと実行の出力フォルダはハードリンクで同じものを指す）。
ログ（samples.jsonl など）に無い値が後から要るときは、`npm run metric -- --runs <実行の出力> --expr "式"` で日次スナップショットを読み直して計算する（スナップショット1つにつき約0.3秒、シードごとに別プロセスで並列に）。二つの実行を渡せば、A/B 比較の判定も付く。
よく使うものは metric.ts の `NAMED` に名前をつけて置く（campStore、vassalCamps、warrenStore、hungryRats など）。

### src/ecology.ts の分割

約9,900行の1ファイルだった Ecology を、クラスの本体（状態のフィールド、セーブしないキャッシュ、定数、型。約770行）と、種・仕組みごとのメソッドのファイル（src/eco/*.ts、35ファイル）に分けた。
各ファイルは `export function 名前(this: Ecology, …)` でメソッドを書き、末尾で `declare module '../ecology' { interface Ecology { … } }` と `Object.assign(Ecology.prototype, { … })` で足す。src/eco/index.ts がすべてを読み込み、world.ts が index を読む。
中身は機械的に移しただけ（`private` は外した）。const enum（Kind など）は esbuild がファイルをまたいでインライン展開する。

## 確かめたこと

- `npm run ab -- --base 4945897 --seeds abc,かしたれ,seed4,seed7 --days 25`（作り直す前のコミットの src/ と、作業ツリーの src/ を、同じログ出力で）：ecology の分割と軽くした二つの所を含めて、4シードとも samples.jsonl と checkpoint.json が25日目まで1バイトも違わない
- 作り直した sim の checkpoint は、作り直す前の sim の checkpoint と1バイトも違わない（abc、2日）
- `npm run ab -- --resume-check 7 --seeds かしたれ,abc --days 12`：状態とログが通しの実行と一致
- `npm test`（21項目すべて OK）、`TEST_FULL=1 npm test`（元の0日目から6日のロード後の再現性のテスト）も OK
- `node build.mjs`（ゲームの1ファイル）もビルドできる
- 四つの保存則：16シード×25日でずれ0

`npm run check` の項目は、ベースの batch で判定の基準を確かめてから置いた。初めに置いた「大ネズミが絶えない（ログの最後の時点で1匹以上）」は、ベースでも大ネズミが0匹と数匹を行き来する（abc、かしたれ）ために満たせなかったので、「来つづける」に替えた。
項目を足すときも、まずベースで満たせることを `npm run check -- --only <名前>` で見ておく（ベースと作業ツリーのバージョンが同じなら、キャッシュの結果を使うので数秒）。

## 測り方

前：作り直す前のコミット 4945897 で、`npm test`、`npm run autopsy -- --seed seed7 --days 20 --kind 2 --cause starve`、`npm run batch`（8シード×25日、16シード×25日）を一つずつ実行して測った（runs/baseline）。
16シードは compare の判定と同じ組（abc、かしたれ、はじまりの洞窟、seed4〜8、seed40、seed41、seed18、seed27、seed23、seed35、seed17、seed30。lib/seeds.ts の SEEDS16）。

後：作り直したコミットで16シード×25日を一度実行してキャッシュに入れ（「前回の実行」）、そのあと小さな変更（`Ecology.GOBLIN_MIN_FOOD` を 1800 → 1500）を入れた状態で、次の順に一つずつ測った（runs/after）：
`npm test` → `npm run probe -- deaths …`（直した直後。ベースのスナップショットから）→ `npm run check` → `npm run ab -- --preset quick` → `npm run ab -- --preset final` → `npm run probe -- deaths …`（final が作業ツリーのバージョンのスナップショットをキャッシュに置いたあと）。

この変更の効果は、quick（8シード、10→18日）では「ゴブリン：中で生まれた」（5対0）と「オーク：飢えて去った」（5対0）が「はっきり増」、
final（16シード×25日）では「オーク：取り立て（回）」（5対0）と「取り立てた食べ物」（7対2）が「はっきり増」で、残りの29の指標は「ばらつきの内」だった。

注意：キャッシュが空のとき（作り直した直後や、`runs/.cache` を消したあと、実行エンジン lib/engine.ts やログ出力 sim.ts を直したあと）は、ベースの結果もまず実行するので、その分長くかかる（quick ならベースの8シード×18日、final なら16シード×25日）。

## そのほか

- batch の出力の既定の名前は `runs/batch-<日時（秒まで）>`、ab は `runs/ab-<preset>-<日時>`。実行ごとに分かれ、ビルドしたツールもキャッシュの中なので、二つの batch を同時に実行してもぶつからない（同じ結果を作るジョブは、ロック用のフォルダで一つにまとまる）。
- ベースとの比較（ab、check、probe のベース）は、ベースの src/ と**作業ツリーの**ログ出力を組み合わせる。ログ出力を変えた（sim.ts に値を足した）ときも、ベースを同じログ出力で再実行して比べられる。
- 細かい使い方は各ツールの先頭のコメントと、CLAUDE.md の「コマンドと分析の流れ」。
