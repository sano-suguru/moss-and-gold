# A/B 比較と分析の流れ

各ツールの使い方は、そのファイルの先頭のコメント（tools/analysis/*.ts）にある。ログファイルの形式は docs/records.md。

## main のキャッシュ

マージ直後で Release「sim-cache」に無いとき（runs/.cache/fetched/log.txt の「Release にまだない」は、フックが動いた時点の話）は、Actions の simcache の実行が終わってから `node tools/analysis/simcache.mjs fetch --ref origin/main` で取得し直す。手元では作らない。
待つ間に main のコードで batch や probe を実行しない（キャッシュの同じフォルダに書きかけのログが残り、あとで取得したものと混ざって二重になる）。待つ間は、コードを読めば分かる直しを実装し、typecheck と test まで進めておく。

## 流れ

1. `npm run ab -- --preset quick`：8シードについて、HEAD の10日目のスナップショットから、HEAD と作業ツリーのそれぞれで18日目まで実行して比べる（`runs/ab-quick-<日時>/compare.md`）。
   **判定が「はっきり」の行だけを効果とみなす**。「ばらつきの内」は、シードごとの展開のばらつきで説明できる程度の差。「1シードの寄与」の列も見る。
2. 気になるものは `npm run probe -- deaths|life|calls|look|stuck` で調べる。使い捨てのスクリプトを書く前に、probe の `--expr` で足りないか見る。要るなら `lib/open.ts` の `openAt(シード, tick)` でその時点の状態を取得する。ログに無い値は、まず `npm run metric` で足りるか見て、足りなければ sim.ts のログ出力に足す。
3. 区切りがついたら `npm run ab -- --preset final`（16シード×25日、0日目から）。保存則のずれは compare.md の末尾に出る。「おかしな兆候」は続けて `npm run batch -- --seeds 16 --days 25`（ab の実行結果をキャッシュから使う。兆候の数は summary.md）。
4. 保存則がずれたら、`tools/analysis/drift.ts`・`manacheck.ts`・`goldcheck.ts` で、ずれた tick と、その tick に変化した生き物を特定する。

```bash
npm run ab -- --base HEAD~1 --seeds abc,かしたれ,seed4,seed7 --days 10   # 挙動を変えないはずのリファクタリング：出力が1バイトも違わないか（違えば終了コード 1）
npm run ab -- --resume-check 7 --seeds かしたれ --days 10              # 7日目で中断・再開しても、通しで実行したときと一致するか
npm run bench -- --warm 1 --repeat 3                                   # 実行速度（読み込んだ直後の JIT の立ち上がりを除く）。変更の前後は続けて測る
```

クラウドのセッションでは、同じビルドでも続けて測るたびに壁時計の時間が2割ほど揺れる。数％の差を見るときは、base と作業ツリーの bench を同時に別々のコアで動かし（`taskset -c 0-1` と `taskset -c 2-3`）、ラウンドごとにコアと起動の順を入れ替えて、比の中央値を見る。変えた関数だけの効果は、`node --cpu-prof` のプロファイルで、その関数の時間を比べる。

## 差が問題かどうかの見分け方

「はっきり」は差があるという意味で、問題があるという意味ではない。判断を PR の説明に書く。

- **画面で困るか**：種が画面から消える、場面が起きなくなる、生き物が動けなくなる、のどれかになるか。数が少し減っただけなら問題ではない。
- **数か、出入りか**：生まれた数・来た数・死んだ数がはっきり変わっても、数そのもの（最後の数、群れや住処の数）がばらつきの内なら、多くは補い合っているだけ。
- **どれだけの時間か**：「0匹だった日数」のような数は、全体（16シード×日数）に対する割合と、いちばん長く続いたシードで見る。
- **1シードの寄与**：差の大半が1シードから来ていれば、そのシードで何が起きたか（例：ドラゴンがいたか）を見てから判断する。main 側の1シードの大きな出来事を、分岐のあとで失っているだけのこともある（base と new のシードごとの数を並べる）。
- **原因を切り分ける**：作業ツリーで新しい仕組みを止めてもう一度比べ、差が残るか消えるかを見る。止めたこと自体が別の変更になるので、`ab` の「何日目のログから違う」も合わせて見る。

## 見せたい場面の発生回数

見せたい場面がシードごとに何回起きたか（compare.md と advreport の表。数え方は tools/analysis/lib/moments.ts）を標準の指標にする。目安は「16シード中12シード以上で、25日に1回以上、できれば数回」。ごくまれな特別イベント（骨の竜など）は対象外。新しい場面を作ったら moments.ts に数え方を足す。
